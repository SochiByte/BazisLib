# Bazis2026Online — Research Rules

**Проект:** Bazis2026Online
**Программа:** Базис-Мебельщик 2026 Online
**Статус документа:** ACTIVE
**Дата:** 2026-07-28

---

## 1. Назначение

Этот документ определяет правила исследования API, runtime, native-кода и внешних механизмов управления Базис-Мебельщик 2026 Online.

Правила обязательны для всех последующих этапов исследования.

---

## 2. Версия программы

Исследование относится исключительно к:

```text
Базис-Мебельщик 2026 Online
```

Результаты других версий Базис не считаются автоматически применимыми к Базис 2026.

Особенно запрещается без проверки переносить сведения из:

```text
Базис 2022
Базис 2021
Базис 2020
старых Script API
старых runtime
сторонних примеров
```

---

## 3. Классификация результатов

Каждый результат должен иметь один из трёх статусов.

### VERIFIED

Факт непосредственно подтверждён.

Источниками подтверждения могут быть:

* выполнение probe-скрипта в Базис 2026;
* наблюдение реального поведения объекта;
* результат Ghidra;
* подтверждённая структура native-кода;
* повторяемый эксперимент.

Пример:

```text
VERIFIED:
Model существует в runtime.
```

---

### DOCUMENTED

Факт присутствует в официальной документации Базис, но экспериментально ещё не подтверждён.

Пример:

```text
DOCUMENTED:
В документации указан SaveModelToFile().
```

До runtime-проверки такой факт не следует считать VERIFIED.

---

### HYPOTHESIS

Предположение, основанное на косвенных признаках.

Пример:

```text
HYPOTHESIS:
Dispatch может использовать IDispatch::Invoke.
```

Гипотеза не должна описываться в документации как установленный факт.

---

## 4. Запрет на выдуманные API

Нельзя считать существующим метод, свойство, класс или функцию только потому, что:

* такое имя логично;
* оно встречается в другой версии Базис;
* оно встречается в интернете;
* оно существует в другом CAD;
* оно предполагается по названию класса;
* оно встречается в непроверенном примере.

До подтверждения используется статус:

```text
HYPOTHESIS
```

или:

```text
DOCUMENTED
```

в зависимости от источника.

---

## 5. Правило экспериментального подтверждения

Для каждого важного API желательно получить:

```text
1. имя объекта;
2. тип объекта;
3. имя метода/свойства;
4. способ вызова;
5. фактический результат;
6. ошибку, если вызов не удался;
7. контекст эксперимента;
8. имя probe-скрипта;
9. файл с результатом.
```

Минимальная запись должна позволять другому исследователю повторить эксперимент.

---

## 6. Ошибки — это результат исследования

Ошибки не удаляются из документации.

Например:

```text
Invalid class typecast
```

является полезным результатом.

Он может указывать на:

* неправильный тип объекта;
* native wrapper;
* специальную коллекцию;
* несовместимость JS-типа;
* необходимость другого способа вызова;
* native implementation detail.

Поэтому ошибки должны сохраняться вместе с исходным экспериментом.

---

## 7. Не смешивать JavaScript API и native API

Следует различать:

```text
JavaScript API
Native API
COM API
Windows API
External API
```

Наличие native-класса не означает, что он непосредственно доступен JavaScript.

Наличие COM-механизма не означает наличие прямого доступа к API Базис.

Каждый уровень должен исследоваться отдельно.

---

## 8. Правило для коллекций

Нельзя считать две коллекции взаимозаменяемыми только потому, что они содержат объекты одного типа.

Например:

```text
Model.Objects
T3DObjectList
```

исследуются независимо.

Если:

```text
Model.Objects.forEach()
```

вызывает:

```text
Invalid class typecast
```

это не означает, что:

```text
T3DObjectList.forEach()
```

также не работает.

И наоборот.

---

## 9. Правило проверки методов

Наличие имени метода недостаточно.

Метод считается рабочим только после проверки:

```text
объект существует
        ↓
метод существует
        ↓
метод вызывается
        ↓
тип аргументов установлен
        ↓
результат получен
        ↓
результат соответствует ожиданию
```

Если метод существует, но вызов не работает:

```text
EXISTS ≠ WORKING
```

Это должно отражаться в документации.

---

## 10. Правило probe-скриптов

Каждый существенный эксперимент должен иметь отдельный probe-скрипт либо быть частью явно обозначенного исследовательского скрипта.

Пример:

```text
bazis_native_collection_probe.js
bazis_objectslist_probe.js
bazis_create_methods_probe.js
```

Probe должен выполнять одну конкретную исследовательскую задачу.

Не следует объединять большое количество неизвестных механизмов в один probe без необходимости.

---

## 11. Правило сохранения результатов

Результат probe не должен оставаться только в Script Editor Log.

Каждый информационный probe должен сохранять результат в файл.

Разделение:

```text
probes\
    исходные .js

output\
    результаты .txt
    результаты .json
    другие результаты
```

Script Editor Log используется только для:

* запуска;
* короткой диагностики;
* подтверждения выполнения;
* кратких сообщений об ошибках.

Основным источником результата считается сохранённый файл.

---

## 12. Имена probe-скриптов

Имя должно описывать задачу исследования.

Предпочтительный формат:

```text
bazis_<object>_<operation>_probe.js
```

Примеры:

```text
bazis_model_runtime_probe.js
bazis_model_objects_enum.js
bazis_objectslist_probe.js
bazis_objectslist_access_probe.js
bazis_native_collection_probe.js
```

---

## 13. Повторяемость

Если результат важен для дальнейшего reverse engineering, эксперимент желательно повторить.

Результат считается более надёжным, если:

```text
один и тот же probe
        ↓
запущен повторно
        ↓
получен тот же результат
```

Если поведение зависит от состояния модели, это должно быть указано.

---

## 14. Контекст эксперимента

Для результатов, связанных с `Model`, необходимо учитывать состояние Базис.

По возможности фиксировать:

```text
открыта ли модель;
есть ли объекты;
есть ли выделение;
какой документ активен;
какое состояние редактора;
```

Особенно важно различать:

```text
метод возвращает NULL
```

и:

```text
метод возвращает NULL в пустой модели.
```

Это могут быть разные случаи.

---

## 15. Reverse engineering

Для анализа native-кода используется:

```text
Ghidra 12.1.2_PUBLIC_20260605
```

Результаты Ghidra также классифицируются:

```text
VERIFIED
HYPOTHESIS
```

Найденная строка или имя функции сама по себе не считается доказательством поведения функции.

---

## 16. Строки бинарного файла

Обнаружение строки в DLL:

```text
"SomeMethod"
```

не доказывает автоматически:

```text
SomeMethod()
```

существование JavaScript API.

Необходимо установить связь:

```text
string
    ↓
reference
    ↓
function
    ↓
call site
    ↓
runtime behavior
```

---

## 17. Dispatch / COM

COM-исследование должно отдельно фиксировать:

```text
COM object
Dispatch wrapper
__vars
__methods
descriptor
DISPID
INVKind
flags
argcnt
native invocation
```

Нельзя автоматически считать:

```text
Dispatch = IDispatch
```

пока это не подтверждено анализом native-кода.

Допустимая формулировка до подтверждения:

```text
Dispatch является runtime-обёрткой COM-объекта.
```

А связь с `IDispatch::Invoke` должна иметь отдельный статус.

---

## 18. DISPID

Полученный `DISPID` фиксируется как отдельный факт.

Например:

```text
Scripting.FileSystemObject.BuildPath → DISPID 10000
WScript.Shell.Run                    → DISPID 1000
MSXML2.XMLHTTP.open                  → DISPID 1
```

Однако наличие `DISPID` само по себе не доказывает конкретную native-реализацию вызова.

Для каждого подтверждённого API желательно использовать структуру:

```text
## Object / Class

Status:
VERIFIED / DOCUMENTED / HYPOTHESIS

Type:

Methods:

Properties:

Arguments:

Return value:

Observed behavior:

Errors:

Source:

Probe:

Output:

Notes:
```

---

## 20. Источник каждого результата

Для каждого существенного результата необходимо по возможности указывать источник:

```text
Probe:
имя JS-файла

Output:
имя файла результата

Ghidra:
имя функции / адрес / reference

Documentation:
название документа или раздел

Runtime:
условия выполнения
```

Это позволяет восстановить происхождение результата.

---

## 21. Запрет на потерю отрицательных результатов

Не удалять сведения о том, что:

* метод отсутствует;
* метод возвращает `undefined`;
* метод возвращает `NULL`;
* вызов вызывает `Invalid class typecast`;
* коллекция не перечисляется;
* объект существует, но недоступен;
* документированный метод не удалось вызвать.

Отрицательный результат может стать ключом к пониманию native implementation.

---

## 22. Разделение факта и интерпретации

Каждая запись должна по возможности разделяться на:

```text
FACT
INTERPRETATION
NEXT TEST
```

Пример:

```text
FACT:
Model.Objects существует.

FACT:
MoveNext() вызывает Invalid class typecast.

INTERPRETATION:
Model.Objects вероятно не является обычным JS iterator.

NEXT TEST:
исследовать native type Model.Objects.
```

Интерпретация не должна записываться как факт.

---

## 23. Изменение статуса

Если HYPOTHESIS подтверждается экспериментом:

```text
HYPOTHESIS
    ↓
VERIFIED
```

Если документированная функция подтверждается runtime:

```text
DOCUMENTED
    ↓
VERIFIED
```

Старый статус не удаляется из истории исследования.

---

## 24. Приоритет исследований

Приоритет отдаётся направлениям, которые могут открыть новые уровни API.

Текущий порядок:

```text
1. ScriptEditor.dll
2. Dispatch
3. native invocation
4. JavaScript ↔ native bridge
5. Model / native collections
6. T3DObjectList
7. полный API Model
8. внешнее управление Базисом
```

---

## 25. Основное правило проекта

Не предполагать, а проверять.

Не смешивать версии.

Не переносить API между версиями без подтверждения.

Не выдавать гипотезу за факт.

Не удалять отрицательные результаты.

Каждый важный результат должен быть воспроизводимым и иметь источник.
